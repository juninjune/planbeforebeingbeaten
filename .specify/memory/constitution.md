# planbeforebeingbeaten Constitution

TV 두뇌 서바이벌 예능의 패자부활전 퍼즐 게임에서 영감을 받은 웹 퍼즐 게임 모음 서비스
(비공식 팬 프로젝트)의 원칙이다. `planbeforebeingbeaten`은 저장소 작업명이며 서비스 표시명은
미정이다. TODO(SERVICE_NAME): 오너가 서비스 표시명을 확정하면 갱신한다.

## Core Principles

### I. 저작권·상표 준수 (NON-NEGOTIABLE)

- 게임의 규칙(메커니즘)만 구현한다. 규칙 설명 문구도 직접 새로 쓴다.
- 원 방송의 프로그램명, 로고, 영상, 음악, 자막 디자인, 세트 디자인, 출연자 이름과 초상은
  서비스 화면, 메타데이터, 홍보물 어디에도 사용하지 않는다.
- 아트, 사운드, 문구는 전부 자체 제작하거나 라이선스가 명확한 소재만 쓴다. 분위기는
  "어둡고 긴장감 있는 두뇌 서바이벌"이라는 장르 톤으로만 연출하고, 특정 방송의 화면을
  식별 가능하게 모사하지 않는다.
- 게임 표시명은 상표로 보호되지 않을 일반명사(예: 울타리 치기, 대칭 퍼즐)면 그대로 쓴다.
  고유명사성 이름과 타사 상표(예: 퍼즐 장르의 등록상표명)는 쓰지 않는다.
- 고유명사성 이름을 가진 게임은 구현 전에 오너에게 알리고 표시명을 확정받는다.
- 서비스에 "비공식 팬 프로젝트이며 원 방송 및 제작사와 무관하다"는 고지를 노출한다.

근거: 규칙은 보호 대상이 아니지만 표현물과 표지는 보호된다. 이 선을 넘으면 서비스 자체를
내려야 한다.

### II. 게임은 플러그인

- 각 게임은 UI와 분리된 순수 규칙 엔진으로 구현한다. 엔진은 "상태 + 행동 → 새 상태"
  형태이고, 결정적이며, 상태와 행동을 직렬화할 수 있어야 한다.
- 엔진은 브라우저 API, 렌더링, 네트워크, 시계, 전역 난수에 의존하지 않는다. 난수가
  필요하면 시드를 입력으로 받는다.
- 각 게임은 공통 게임 인터페이스를 구현해 레지스트리에 등록한다. 새 게임을 추가할 때
  기존 게임의 코드를 수정하지 않아야 한다.
- 같은 엔진을 향후 멀티플레이 서버의 검증 로직으로 그대로 재사용할 수 있어야 한다.

근거: 게임 수가 늘어나는 서비스이고, 멀티플레이에서 클라이언트와 서버가 같은 판정을
내려야 한다.

### III. 작동 확인 우선, 단계적 확장

- 마일스톤 1은 "울타리 치기" 1인 플레이다. 퍼즐 한 판을 풀고, 정답 판정과 완성 시간이
  나오면 완료다.
- 멀티플레이는 마일스톤 1 이후의 별도 마일스톤이다.
- 현재 마일스톤에 필요 없는 기능(계정, 랭킹, 방 만들기 등)은 만들지 않는다.
- 다만 엔진과 퍼즐 생성은 멀티플레이를 막지 않는 구조로 둔다. 퍼즐은 시드로 재현할 수
  있어야 하며, 그래야 여러 플레이어에게 같은 판을 줄 수 있다.

근거: 작동하는 한 게임이 구조 전체를 검증한다. 미리 만든 기능은 검증되지 않은 가정이다.

### IV. 규칙 엔진 테스트 필수

- 규칙 판정(정답 검증, 완성 판정, 잘못된 행동 거부)은 자동 테스트로 검증한다.
- 퍼즐 생성기는 생성한 퍼즐의 풀이 가능성과 유일해 여부를 자동 테스트로 검증한다.
- 엔진 테스트가 실패한 상태로 병합하지 않는다.
- UI는 실제 브라우저(모바일 화면 크기 포함)에서 직접 조작해 확인한다.

근거: 퍼즐 게임에서 판정 오류는 게임 자체의 고장이다. 순수 엔진이라 테스트 비용이 낮다.

### V. 모바일 우선·간편 접속

- 설치와 가입 없이 링크만으로 바로 플레이할 수 있어야 한다.
- 모바일 브라우저의 터치 사용성이 원작 재현도보다 우선한다. 판 크기, 조작 방식 등이
  충돌하면 모바일에서 쓰기 편한 쪽을 기본값으로 한다.
- 원작에 가까운 설정(예: 10x10 판)은 선택 옵션으로 제공한다.

근거: 사람들이 가볍게 접속해 플레이해 보는 것이 서비스의 목적이다.

## 게임 규칙 기준

- 게임 규칙의 기준은 오너가 확인해 준 내용이다. 팬 커뮤니티나 위키의 서술은 참고
  자료이고, 오너 확인 없이 규칙으로 확정하지 않는다.
- 확인되지 않은 규칙 항목은 spec에 "미확인"으로 표시하고, 추측으로 채우지 않는다.
- 울타리 치기의 확정 규칙: 참가자 모두 같은 판을 푼다. 제한 시간은 없다. 먼저 완성한
  사람이 이긴다. 오답 패널티는 없다. 원작의 판 크기는 10x10이다.

## 개발 워크플로

- 기능은 Spec Kit 순서(specify → plan → tasks → implement)로 진행한다.
- 설계·기획 결정은 옵션 제안, 토론, 오너의 명시적 확정을 거친 뒤에 문서화하고 구현한다.
  미결 항목을 임의로 채워 진행하지 않는다.
- 각 plan은 이 헌법의 원칙 I부터 V까지를 충족하는지 점검하고, 벗어나는 부분은 사유를 적는다.

## Governance

- 이 헌법은 프로젝트의 다른 관행과 문서보다 우선한다.
- 개정은 오너의 승인이 있어야 하며, 개정 시 버전과 개정일을 갱신한다.
- 버전은 시맨틱 버저닝을 따른다. 원칙의 삭제나 재정의는 MAJOR, 원칙이나 섹션의 추가와
  실질적 확장은 MINOR, 표현 정리와 오탈자 수정은 PATCH다.
- spec, plan, 코드 리뷰는 이 헌법의 준수 여부를 확인한다. 특히 원칙 I(저작권·상표)은
  새 게임, 새 아트, 새 문구가 들어올 때마다 점검한다.
